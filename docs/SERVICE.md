# Service functions

The **Service** page (and `klemme15 service`) runs functions that change something in the car: service reminder resets, battery registration, calibrations, adaptation resets, learning routines, bleeding, diesel service work and component tests. **[The full list (53 functions)](SERVICE-FUNCTIONS.md)** covers the E46 and E90-family engines, gearboxes, DSC, xDrive, body and climate modules.

They live in [`src/Klemme15.Data/db/service.json`](../src/Klemme15.Data/db/service.json), generated by [`tools/service-catalog/build_service.py`](../tools/service-catalog/build_service.py) from recipes written in our own words.

## How a function runs

1. **Availability.** Klemme15 finds the module the function talks to and its version (the name the module reports in EDIABAS mode, otherwise the most likely version from its part number and engine). A function is offered only for versions it lists.
2. **Checks.** Klemme15 reads the battery voltage, engine speed and road speed, plus the ignition state where the cable reports it. Anything it can't measure, you confirm by hand. Failed checks block the function.
3. **Confirmations.** Each function lists things only you can check ("the wheels point straight ahead"). Each one must be ticked.
4. **Choices.** Some functions ask which item (oil, brake pads...), which cylinder, which brake circuit, or for an injector's printed code. Only the choices your module version supports are offered.
5. **Run.** The function runs once:
   - **With your BMW files** (EDIABAS mode): Klemme15 runs BMW's own jobs for your module version from your files, step by step, waits where a part has to run or a module has to learn, and reads back the result where BMW provides one.
   - **Timed tests always end cleanly.** Where a part is switched on by Klemme15 (fan, pump, valve, a cylinder cut-out), the function either uses BMW's built-in timeout or runs BMW's stop job afterwards, including when a step fails or you press Stop.
   - **Without BMW files**: only where the exact request is documented for those module versions (currently battery registration on E90-family engines: KWP2000 StartRoutineByLocalIdentifier `31 30 00 10 00`, positive reply `71 30`).
6. **Result.** You see the module's answer. Every request and reply is in the traffic log.

Each run needs fresh checks and confirmations.

## Experimental

A function is marked `"verified": false` until someone has run it on a real car with Klemme15 and confirmed it worked. Unverified functions only run after you switch on **experimental functions** (bottom left of the Service page, or `--experimental` on the command line). If you run one, please [report what happened](../CONTRIBUTING.md#report-a-test-drive) with your traffic log, so it can be marked verified.

## What is not included, on purpose

No coding, no flashing, nothing that writes to the immobiliser (CAS/EWS), the VIN, the odometer, or changes the car's configuration. (Writing a diesel injector's printed correction code is included: it is a calibration value for a replaced part, which ISTA also handles as a service function.) A battery of a different type or capacity needs the vehicle order changed (coding), which Klemme15 doesn't do. A test in `tests/Klemme15.Tests/ServiceTests.cs` rejects catalog entries that look like coding, flashing or immobiliser jobs.

## How recipes are checked

Each recipe names a BMW job, the arguments we send, and the exact argument list the job must have (`sig`). The generator only gives a module version the recipe when that version's job takes exactly those arguments, so a version whose job expects something different (a percentage instead of on/off, a bit mask instead of a cylinder number) never gets our values. Stop jobs must exist on the version too. Every recipe was also reviewed against BMW's argument descriptions (ranges, units, required stop jobs, preconditions such as "engine speed 0" or "idle").

## Adding a function

Add a recipe to `tools/service-catalog/build_service.py` and run it with the bmw-unified-db SQLite file (download `bmw.sqlite.gz` from [its releases](https://github.com/gediz/bmw-unified-db/releases) and unpack it). Each function has:

- `id`, `title`, `category`, `module` (short module id, e.g. `DME`, `DSC`, `EGS`, `FRM`), `summary`, `when`, `risk` (`low`, `medium`, `high`), `verified: false`.
- `before` and `after`: steps in plain words.
- `checks`: `ignition`, `engineOff` or `engineRunning`, `minVoltage`, `stationary`, and `confirm` items.
- `inputs`: choices (`choice`) or typed values (`text` with a `pattern`) the user provides; `{id}` in a job name or its arguments is replaced by the value, translated per module version through `map`.
- recipes (`R(...)`): the job, arguments, expected argument list (`sig`), extra steps (`then`), `stop` jobs, `wait` seconds, and `only`/`exclude` to limit module versions. `native` (hex) and `expect` only when the request is documented for exactly those versions; native requests may only start a routine (`31`) or control an output (`30`).

Look up job names and arguments in the job lists of your own BMW files (`klemme15 jobs <variant> --ediabas <folder>`) or in bmw-unified-db; write descriptions in your own words. Never edit `service.json` by hand: rerun the generator.
